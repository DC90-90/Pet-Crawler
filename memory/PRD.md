## Original Problem Statement
SaaS web application "Daleel" for Saudi store owners to track and monitor competitor stores in the Saudi market (Salla, Zid platforms). Monitor product prices, stock/quantity, best sellers, categories, and discounts. Multi-tier crawler architecture; strict product matching (Barcode → SKU priority).

**User language**: English. **Production**: https://saudi-pets-monitor.emergent.host (user manages deployments — NEVER save to GitHub or redeploy).

- **Aug 1 2026 — iter73d "My prices should include VAT everywhere"**:
  * **Symptom (production)**: my-store prices displayed inc-VAT on some tabs and ex-VAT on others. Client asked for consistency across all tabs and cards.
  * **Two root causes**:
    1. `resolve_own_price` (crawlers.py) intentionally left rows at ex-VAT when Zid's `is_taxable` was `None` (tristate "unknown"), tagging them `merchant_unknown_tax`. Zid's Merchant API doesn't always populate the flag, so a subset of `my_products` and `product_snapshots` rows stayed ex-VAT while nearby storefront-covered rows were inc-VAT — the mixed-basis display.
    2. `_fetch_zid_api_catalog` collapsed `raw.price = sale_price OR list_price`, throwing away the LIST price on on-sale items. Downstream, `original_price` fell back to the sale price → strikethrough / discount % rendered blank or wrong for the very products it should have highlighted.
  * **Fix — resolver policy shift + list-price preservation**:
    - `resolve_own_price` now returns a 4-tuple `(price, sale_price, original_price, basis)`. `original_price` is the LIST price grossed to the SAME VAT basis as `price` — so callers never reconstruct the strikethrough after the fact.
    - Retired basis `merchant_unknown_tax`. New basis `merchant_assumed_inc_vat` covers `is_taxable=None` and grosses up per Saudi retail default (VAT applies to virtually all retail goods). Explicit `is_taxable=False` still stays flat with basis `merchant_non_taxable`.
    - `_fetch_zid_api_catalog` preserves `list_price` as a separate field on each raw row; the sync loop forwards it as `merchant_list_price=` to `resolve_own_price`; `own_resolved_price` becomes a 4-tuple; snapshot writer unpacks list into `original_price` so `original > price` is true whenever there IS a genuine sale.
    - `my_products` writes carry `original_price` alongside `price` / `sale_price` for both new inserts and updates. The `admin/own-store-vat-backfill` endpoint persists `after_original_price` too.
  * Tests: `tests/test_vat_all_tabs.py` (13 new tests: 4-tuple contract, list-price preservation, sync-loop wiring, snapshot writer wiring, "no ex-VAT ever leaks for taxable/unknown paths" invariant, backfill endpoint update). `tests/test_own_store_vat_basis.py` + `test_own_snapshot_vat.py` updated to the new 4-tuple + basis semantics. 97/97 curated regression suite green; backend healthy.
  * **Migration**: existing rows in production carry the old `merchant_unknown_tax` basis. Once redeployed, an operator should run `POST /api/admin/own-store-vat-backfill?dry_run=false` to re-resolve every row via the new policy — this converts every `merchant_unknown_tax` row to `merchant_assumed_inc_vat` and grosses up its price × 1.15.
