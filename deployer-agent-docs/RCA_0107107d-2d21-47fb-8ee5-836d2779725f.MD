# RCA — HTTP 500 on GET /api/my-products (production)

## Identifiers (observed)
- Deployment: `saudi-pets-monitor` (id `d92f6fcd-0827-4252-9842-f2112a2b0a73`)
- Active/serving run: `0107107d-2d21-47fb-8ee5-836d2779725f` (status success)
- Image: `us-central1-docker.pkg.dev/emergent-default/customers-app/saudi-pets-monitor:0107107d-2d21-47fb-8ee5-836d2779725f`
- Template: `fastapi_react_mongo_shadcn_base_image` · frontend: cloudflare · tier_2 · cluster target-3
- Mongo db_name (observed): `saudi-pets-monitor-daleel_pets`
- This run picked up CORS_ORIGINS correctly and serves 200 elsewhere — the 500 is endpoint-specific, NOT auth/CORS. `preview_health_check` on the exact URL returns 401 (auth wall, app up), confirming it is request/data-path specific, not a boot failure.

## Symptom
- `GET /api/my-products?sort_by=revenue_est&sort_order=desc&limit=100&offset=0&days=30` → repeated **500 Internal Server Error**.
- `GET /api/my-products-list?page=1&limit=1` → **200** reporting 2832 products.
- Screenshot "Request failed / results unavailable" is the frontend reacting to the backend 500.

## Root cause (PROVEN from production traceback)
The 500 is a **MongoDB read timeout** on the price-cohort aggregation. The Motor client is configured `socketTimeoutMS=45000` (`backend/server.py:120`); the aggregation does not return within 45s, so pymongo raises `TimeoutError: The read operation timed out` and FastAPI returns 500.

It is NOT auth, NOT CORS, and NOT the observer/write guard. The cacheable branch's cache WRITE (`_store_dashboard_cache`) is wrapped in `try/except: pass` (around `backend/server.py:3507-3509`), so a default-denied cache write cannot raise the 500 — the failure is purely the live READ aggregation exceeding the socket timeout.

### Offending function / file / line
The aggregate that times out lives at **`backend/price_cohort.py:135`**, inside `build_cohorts()` (def at line 113), reached via `comparison_views.context()` (`comparison_views.py:14`):
```python
cursor = db.product_snapshots.aggregate([
    {"$match": {"store_id": {"$in": active}, "crawled_at": {"$gte": now - timedelta(days=180)}}},
    {"$sort":  {"crawled_at": -1}},
    {"$group": {"_id": {"$ifNull": ["$offer_id", {"store": "$store_id", "sku": "$sku"}]},
                "latest": {"$first": "$$ROOT"},
                "historical_max": {"$max": {...}}}},
    {"$replaceRoot": {...}},
    {"$project": {**FIELDS, "historical_max_price": 1}},
], allowDiskUse=True).batch_size(2000)
```

### Why it is slow / why it times out (evidence)
- The snapshot window is **hardcoded to 180 days** in `build_cohorts` and is independent of the request's `days=30` (that param only scopes the orders/sales window downstream). So every call scans ~180 days of `product_snapshots` for all active competitor stores.
- `product_snapshots` indexes (observed via `list_indexes`): `_id_`, `crawled_at_1`, `sku_1_crawled_at_-1` = `{crawled_at:-1, sku:1}`, `product_id_1`, `store_id_1_crawled_at_-1` = `{crawled_at:-1, store_id:1}`. **No index leads with `store_id`.** The `$match` is `store_id $in [many] AND crawled_at >= now-180d`; with only `crawled_at`-leading indexes this is a very wide range scan, followed by a blocking `$sort`+`$group` with `allowDiskUse=True`.
- Collection scale: an unfiltered `count` on `product_snapshots` itself **exceeded the query time limit** (query_timeout) — corroborating that the collection is large enough that this aggregation blows the 45s socket cap.

### Why /api/my-products-list is fine
`/api/my-products-list` is a lightweight paginated `find()` over `my_products` (no cohort aggregation over `product_snapshots`), so it returns 200 with the 2832 count.

## Secondary finding (same root cause)
`GET /api/price-intel/dashboard?...` also 500s; its stack passes through `_serve_page_cache` (`backend/server.py:2720`) into the same `product_snapshots` aggregate → same `TimeoutError`.

## Suggested fix (for E1 / main agent — code; not applied here)
1. Add a supporting compound index leading with the match's equality field: `product_snapshots {store_id:1, crawled_at:-1}` so the `$match` (store_id $in + crawled_at range) + `$sort crawled_at:-1` is index-served instead of a wide scan. (Index creation is a DB/migration change — recommended, NOT performed, per read-only constraint.)
2. Reduce scanned volume: the 180-day snapshot window in `build_cohorts` (`price_cohort.py:135`) is hardcoded regardless of `days`; consider narrowing or parameterizing it, and/or pre-aggregating latest-offer-per-store into a materialized collection.
3. Serve `/my-products` from `dashboard_cache` more reliably so a cache miss/stale does not force a 45s live compute on the request path (precompute/refresh out-of-band). Note the current cache write is best-effort (`try/except: pass`) and, combined with the observer default-deny on writes, the cache rarely populates — every request falls back to the expensive live compute.
4. Add `maxTimeMS` to the aggregation (pattern already used elsewhere via `SELLER_QUERY_MAX_MS`) so it fails fast with a clear error instead of a bare socket-timeout 500.
