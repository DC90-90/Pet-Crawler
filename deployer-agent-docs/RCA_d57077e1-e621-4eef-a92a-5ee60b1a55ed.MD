## 3. Root cause — Problem 1 (My Products 503)
The P0 candidate **works as a guardrail but did NOT resolve the underlying timeout**. It only converted the old uncaught 500 into a clean, retryable 503 (`price_query_timeout`) and returns "unavailable, not empty" (hence the exact banner "Request failed. Results are unavailable, not empty.").

The real cause is still an **unbounded cold scan** in `price_cohort.build_cohorts` → `snapshot_pipeline(active, now)` on collection `product_snapshots`:
```
$match {store_id: {$in: <all active competitor stores>}, crawled_at: {$gte: now-180 days}}
$sort  {crawled_at: -1}
$project ... ; $group (first/min/max over 180d) ; $replaceRoot ; $project
allowDiskUse=true, maxTimeMS=SNAPSHOT_QUERY_MAX_MS(15000), batch_size(2000)
```
The 180-day window across every active store is too large to finish inside the 15s server `maxTimeMS` / 20s request deadline, so the driver hits a socket NetworkTimeout on a getMore. "Cold-scan volume unchanged" (per P0_MY_PRODUCTS_TIMEOUT.md) is confirmed in production.

### Independent corroboration (count/correlation evidence)
- A read-only `count` on `product_snapshots` in the **production** DB (`saudi-pets-monitor-daleel_pets`) **itself timed out** (`query_timeout: query exceeded the time limit`) — the collection volume alone defeats a bounded query.
- `list_indexes(product_snapshots)` → `_id_`, `crawled_at_1`, `sku_1_crawled_at_-1` ({crawled_at:-1,sku:1}), `product_id_1`, `store_id_1_crawled_at_-1` ({crawled_at:-1,store_id:1}). **There is NO index leading with `store_id`.** The pipeline filters `store_id $in [...] + crawled_at >= 180d`; the best available index leads with `crawled_at`, so the $match/$sort scans a very large candidate set.
- `build_cohorts` is the **shared price engine**: `comparison_views.context` → `build_cohorts` is reached by the My Products path and would be reached identically by Price & Market Intel / Market Share. Any tab that invokes it will hit the same `price_query_timeout`. In the observed 12h window only `/api/my-products` was exercised (other price tabs were not reached — see Problem 2), so no separate PriceIntel/MarketShare 5xx was logged, but they share the same fault.

## 4. Root cause — Problem 2 (navigation collapsed; Market Share + other authorized tabs hidden)
This is a **frontend gating** issue, independent of role/allowed_pages. Evidence from the serving run's source:

`/api/release` (live, 200) returns: `mode:"observer"`, `price_comparison_only:true`, all `capabilities:*=false`, `control_revision:0`, `writer_epoch:0`, `automatic_refresh_status:"disabled"`.

`frontend/src/components/Sidebar.jsx` nav filter:
```js
if (item.to === "/alerts" && !release.capabilities.email) return false;
if (release.price_comparison_only && !["/", "/insights"].includes(item.to)) return false;
```
Because `price_comparison_only === true`, **every nav item except `/` (My Products) and `/insights` (Price & Market Intel) is removed** — including `/market-share` (Market Share), `/scanner`, `/discounts`, `/alerts`, `/stores`, `/import`. The super_admin **Users** link is also hidden by `user?.role === "super_admin" && !release.price_comparison_only`. Settings remains because it is gated only by `canAccessPage(user,"settings")`. This exactly reproduces the screenshot (sidebar = My Products + Price & Market Intel + Settings only).

`frontend/src/components/ReleaseBoundary.jsx` compounds it:
```js
const allowed = ["/", "/price-intel", "/insights", "/settings"];
if (!release.price_comparison_only || allowed.includes(pathname)) return children;
return <...>Unavailable in this release<...>;
```
So even if Market Share were linked, visiting `/market-share` renders "Unavailable in this release" (it is not in `allowed`; note also the stale `/price-intel` entry vs the nav's `/insights`).

This contradicts the stated requirement that **all authorized tabs (incl. Market Share) stay visible in read-only mode with unavailable actions disabled**. The current code *hides* them instead of showing-but-disabling. Fix belongs in the frontend gating (Sidebar.jsx + ReleaseBoundary.jsx), not in secrets/infra. (Main will inspect/prepare the nav source edit.)

## 6. Recommended fixes
### Code (E1/main — redeploy required)
1. **Resolve the cohort timeout (root cause of the 503).** Reduce scanned volume in `price_cohort.snapshot_pipeline`/`build_cohorts`: narrow the 180-day window or push eligibility/latest-selection earlier; and/or precompute/materialize the cohort snapshot so the request path reads a small, bounded result instead of a 180-day cross-store aggregate. The current `maxTimeMS=15000` / 20s deadline only bound the failure, they do not make it succeed. Verify with `explain()` that the chosen `$match` is index-covered. (Broad server.py refactor is out of scope per instruction.)
2. **Navigation read-only visibility.** In `Sidebar.jsx` stop hiding authorized tabs when `price_comparison_only` — render them (respecting `canAccessPage`/role) but mark actions disabled; and in `ReleaseBoundary.jsx` add `/market-share` (and reconcile `/price-intel` vs `/insights`) to the allowed/read-only set so authorized pages render read-only rather than "Unavailable in this release."

### User (Deployment Panel → Resources / DB) — supporting, NOT the sole fix
3. **Add a supporting index** `{store_id: 1, crawled_at: -1}` on `product_snapshots` so the pipeline's `$match(store_id $in, crawled_at>=180d)` + `$sort(crawled_at:-1)` is index-served. This is a data/index change (I am read-only and cannot apply it); it complements fix #1 but will not by itself fix an inherently oversized 180-day cross-store scan. A tier change is NOT indicated — no OOM/eviction/CPU-throttle was observed; the failure is query latency, not a tier ceiling.
