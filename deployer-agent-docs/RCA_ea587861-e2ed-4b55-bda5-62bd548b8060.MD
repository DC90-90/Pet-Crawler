## 3. Why index-backed plans still time out
Both plans: `collection_scan=false`, `blocking_sort=false`, but both contain a `GROUP` stage.
- Primary: GROUP > PROJECTION_SIMPLE > FETCH > IXSCAN(crawled_at_1).
- Alternative: GROUP > PROJECTION_SIMPLE > FETCH > SORT_MERGE > 10x IXSCAN(store_id_1_crawled_at_-1).
`$group` is a blocking full-pass accumulation: the server must FETCH every matched 30-day document through the index scan before it can emit the first batch, so the initial aggregate cannot return within the socket read timeout. The SORT_MERGE variant fans across ~10 store_id branches but still FETCH+GROUPs the entire working set. QueryPlanner shape is healthy; the wall is server-side EXECUTION COST over the production data volume — which queryPlanner alone does not prove, but the live NetworkTimeout on get_cursor + ALTERNATIVE_FAILED do.

## 5. Fixes
### A. Code (E1) — primary, no new authorization needed
`price_cohort.py::_build_cohorts` (line 188): the initial cohort `aggregate` must return its first batch within the socket read budget. Options that need no mutations:
- Shrink the matched/FETCHed working set before `$group` (tighter server-side predicate; the days=30 window FETCHes too many docs on BOTH index paths).
- Decompose the single blocking `$group` — e.g. iterate cohorts per store_id with bounded concurrency rather than one SORT_MERGE/GROUP across all stores, so each aggregate returns a first batch quickly.
- Set an explicit per-operation server timeout (maxTimeMS) so a slow read fails fast/deterministically instead of hitting the raw socket read timeout, and keep the no-partial/no-empty contract.
