## 6. INDEX KEY ORDER — SETTLED, earlier "missing store-leading index" RETRACTED
- METHOD (artifact-proof): `list_indexes` returns each index's **`name` as a plain string** (immune to the JSON dict-key sorting that corrupted the `key` object display). MongoDB default index naming = fields joined **in key order** `field_dir[_field_dir...]`. Therefore:
  - `store_id_1_crawled_at_-1` ⟹ key order **[(store_id,1),(crawled_at,-1)] — store_id LEADING**.
  - `sku_1_crawled_at_-1` ⟹ [(sku,1),(crawled_at,-1)] — sku leading.
- CROSS-CHECK (source): `server.py` INDEX_SPECS + `integrity_indexes.py`/seed `create_index` declare these as ORDERED tuples `[("store_id",1),("crawled_at",-1)]`, `[("sku",1),("crawled_at",-1)]`. Deployed names match the auto-name of these tuples EXACTLY ⟹ auto-named ⟹ name encodes true BSON order.
- CONCLUSION: a **store_id-leading compound index EXISTS** on deployed `product_snapshots`. The `{crawled_at:-1, store_id:1}` / `{crawled_at:-1, sku:1}` displays were the metadata tool alphabetically sorting the key object (crawled_at < sku, crawled_at < store_id). **The duplicate/"missing store-leading" index recommendation is WITHDRAWN — unproven and likely already present.**
